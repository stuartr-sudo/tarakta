## Open issues / what to investigate next

### 1. The 2-hour scratch rule still fires on flat-but-not-favorable trades

The MFE-based scratch fix (`ae04581`, P3) only protects trades that briefly went into profit (MFE ≥ 0.3R at some point in the 2h window). Trades that stay roughly flat for 2h still get scratched. The first live trade of v2 (AVAX short on 2026-04-28) hit this exact pattern: entered at $9.2328, scratched at $9.252 after exactly 2 hours, MFE = 0.0R, loss −$64.55.

Course rule per Lesson 13 ([47:00]): "substantial profit within two hours." The MFE fix interpreted "within" as a window — correct. But the threshold (0.3R) and the binary scratch behavior may be too aggressive for trades that haven't BREAKED but also haven't gone significantly favorable.

Possible directions:
- Lower MFE threshold (0.15R)
- Use elapsed-bar-based scratch rather than time-based (e.g. scratch after 4-6 1H bars without favorable momentum)
- Allow scratch only if drawdown from entry exceeds X% (so flat-but-not-broken trades survive)

### 2. Sanity agent disabled — open question whether/how to re-enable

The deterministic engine alone produced 1 trade in ~36 hours of live running (low end of backtest expectation of ~2/day). When we re-enable the agent:
- Current rubric_v=3 prompt is calibrated for broken-architecture data; will likely over-veto
- Agent v2 design (in deleted `MM_SANITY_AGENT_V2_DESIGN.md` — preserved in commit history) proposed reasoning-based + variable sizing but engine doesn't have variable-sizing plumbing
- Practical path: rewrite the rubric to use the new gate framework outputs as inputs; keep binary APPROVE/VETO; recalibrate Rubric 8 outcome stats on the new clean data once 30+ trades accumulate

### 3. Dead-factor zero-out not yet shipped to production

Backtest evidence (post-fix) is +$91k on 90d × 20 sym. The change is a single-file edit to `mm_confluence.py` — set the four dead-factor weights to 0, recompute `MAX_POSSIBLE` and `AVAILABLE_MAX`. Can be deployed as a follow-up.

### 4. Heavy per-symbol P&L concentration

APT alone produces 30-50% of total P&L across every backtest config. If APT's market structure changes, a meaningful chunk of edge disappears. Worth thinking about whether the strategy is genuinely course-faithful or accidentally fitting APT's specific behaviour. FIL, BCH, TRX have similar concentration.

### 5. INSTANCE_ID mismatch was fixed but worth flagging in code

`tarakta-mm` instance_id had no `engine_state` row at start of session — engine reads but never writes (`upsert_engine_state` only called from dashboard `api.py`). Solved by direct SQL insert. The bot itself never auto-creates its own row, which is a fragility — first-time deploys to a new INSTANCE_ID need a manual seed. Not a bug per se, but worth a small fix: have the engine `upsert_engine_state(...)` once at startup if no row exists.

## Handover notes

This document captures the state on 2026-04-28. Anyone picking up the project from here should:

1. **Not lower the `mm_gate_threshold` from 3.** It's the empirically-validated sweet spot from a 365-day backtest. Lowering admits the lowest-quality setups; raising starves the funnel.
2. **Treat the AVAX scratch as the canonical example** of what's still wrong with the 2h scratch logic. Any rework of the scratch rule should be tested against this specific trade pattern.
3. **Re-test dead-factor zero-out on production** before deciding whether to ship it. The backtest evidence is strong but the live behavior with all gates active hasn't been observed.
4. **Don't pursue predictive entry without quality gates already filtering.** Three independent backtests proved naive predictive is catastrophic; only by layering predictive on top of the existing reactive funnel is there any chance of edge.
5. **Course transcripts under `docs/courses/` are the source of truth.** Any rule, gate, or scoring choice in the codebase should be cite-able to a specific lesson + timestamp. If it isn't, it's bot-author invention.
